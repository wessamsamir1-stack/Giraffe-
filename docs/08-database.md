## ٣. محرك المطابقة — أهم جزء

### شرط الترشيح المزدوج

الكارت **ما بيظهرش أبداً** إلا لو الشرطين اتحققوا مع بعض:

```
1. منتجهم بيطابق حاجة في قائمة رغباتي     ←  my_interest    ≥ 50
2. منتجي بيطابق حاجة في قائمة رغباتهم     ←  their_interest ≥ 50
```

**الشرط التاني هو السر كله.**

من غيره احتمال الماتش = احتمال الإعجاب **تربيع**. عند إعجاب ٥٪، الماتش ٠.٢٥٪ — يعني المستخدم بيسحب ٤٠٠ كارت من غير ولا ماتش وبيمسح التطبيق.

مع الشرطين النسبة بتقفز لـ ١٥–٢٥٪.

### الاقتران الحتمي

لكل منتج عندهم بنختار **منتج واحد** من عندي، والاختيار حتمي:

```sql
order by their_interest desc, mi.id asc
```

ده مقصود ومهم جداً: لازم أنا أشوف الزوج (منتجي M ↔ منتجهم T) وهم يشوفوا **نفس الزوج بالظبط**، وإلا الماتش المتبادل مش هيتحقق أبداً.

مثبت في الاختبار: وسام بيشوف الآيفون مقابل البلايستيشن، وأحمد بيشوف البلايستيشن مقابل الآيفون.

### نسبة التوافق

| الوزن | العامل |
|---|---|
| ٣٥٪ | قد إيه أنا عايز منتجهم |
| ٣٥٪ | قد إيه هم عايزين منتجي |
| ١٥٪ | تقارب القيمة (بعد الفرق النقدي) |
| ٨٪ | المسافة |
| ٧٪ | ثقة ونشاط الطرف التاني |

**الرغبة المتبادلة = ٧٠٪ من الدرجة.** الباقي بيرتّب بين الصفقات الممكنة، مش بيقرر إذا كانت ممكنة أصلاً.

### الدوال

```sql
select * from public.get_deck(auth.uid(), 20);

select public.record_swipe(
  '<their_item>', '<my_item>', 'interested'
);
-- {"ok": true, "matched": true, "match_id": "..."}

select public.undo_last_swipe();
```

## ٤. تطبيع النص العربي — ضروري مش تحسين

من غيره

`آيفون` و `إيفون` و `أيفون`

بيبقوا **ثلاث كلمات مختلفة تماماً**، وأهم مطابقة في المحرك بتفشل.

الدالة

`normalize_ar`

بتوحّد الألف بأشكالها والياء والتاء المربوطة، وبتشيل التشكيل والتطويل.

### الكلمة المفتاحية

التشابه المتماثل

`%`

مش مناسب: "ايفون" مقابل "ايفون 15 برو 256 جيجا" بيدي درجة منخفضة لأن الطولين مختلفين جداً.

الصح هو **تشابه الكلمة داخل النص**

`<%`

ومعاه احتواء نصي مباشر للحالة السهلة. مطبق في

`keyword_hits_title`

**دي كانت أول علة اكتشفناها في الاختبار:** الدرجة كانت بتطلع 70 بدل 100 لأن التشابه المتماثل فشل. لولا الاختبار الفعلي كانت هتعدي.

## ٥. قرار: ليه مفيش PostGIS

الخطة الأصلية كانت PostGIS. اتغيّرت للأسباب دي:

**١.** إحنا **مش بناخد موقع دقيق** أصلاً — قرار خصوصية. بنخزن نقطة مزحزحة عشوائياً في حدود كيلومتر عبر

`jitter_point`

**٢.** المطابقة مقيّدة بالمدينة أولاً، والمسافة ترتيب ثانوي.

**٣.** على المستوى ده، مؤشر على

`(city_id, lat, lng)`

مع هافرساين بيدّي نفس النتيجة بجزء من التعقيد.

**مسار الترقية:** لما تنزل **الخريطة** في المرحلة التانية، بنضيف عمود

`geography`

ومؤشر GiST جنب الأعمدة الحالية — من غير كسر أي حاجة.

نفس المنطق مع

`pgvector`

مؤجل للتوصيات الذكية في المرحلة التانية.

## ٦. الأمان

### الحماية على مستوى الصف

**مفعّلة على كل جدول بدون استثناء.** الاختبار بيتأكد من ده صراحة:

```sql
select count(*) from pg_tables t
  join pg_class c on c.relname = t.tablename
 where t.schemaname = 'public' and not c.relrowsecurity;
-- لازم = 0
```

### بيانات خاصة تماماً

| البيانات | القاعدة |
|---|---|
| قائمة الرغبات | صاحبها فقط — بيانات تنافسية، لو ظهرت تتستغل في التسعير |
| السحبات | صاحبها فقط — "مين عمل لك إعجاب" ميزة مدفوعة لاحقاً |
| جهة الطوارئ | صاحبها فقط، **بدون أي استثناء** |
| المصطلحات المحظورة | مفيش وصول من العميل خالص |

### إخفاء درجة الترتيب على مستوى العمود

`ranking_score`

مخفي عن المستخدم عبر صلاحيات الأعمدة مش RLS (لأن RLS بيشتغل على الصفوف).

لو ظهر، هيتحول لهدف للتلاعب ولمصدر لا ينتهي من الشكاوى — ودي بالظبط المشكلة اللي خلّتنا نلغي الـ Trust Score الرقمي من الأساس.

### الحظر بيكسر كل القواعد

مفروض في القاعدة مش في الواجهة:

- محفّز بيقفل كل الغرف بين الطرفين فوراً
- بيفك حجز المنتجات
- سياسة إرسال الرسائل بترفض الغرف المقفولة بالحظر أو المجمّدة ببلاغ

يعني حتى لو حد كلّم الـ API مباشرة، مش هيعدي.
